### 将双人标注改为个人项目可执行的一致性验证

- 删除“双人独立标注、第三人仲裁、加权 Cohen's kappa、自动总分与人工共识相关性”等需要多人参与的承诺。
- 依据任务书“一致性验证可采用人工一致程度或同一输出多次评估波动”的要求，选择重复稳定性路线。
- 根据 2026-09-11 截止版规模，对固定的 12 份分层输出各运行 Hy3 裁判 3 次，固定模型版本、prompt、参数和输入顺序，共 36 次评测。
- 报告每个维度及总分的均值、标准差、最大分差和维度等级一致率；保留“百分制总分平均标准差不超过 5 分”的目标，不再把小样本 ICC 作为硬性验收指标。
- 增加顺序鲁棒性检查：成对比较时交换好/中/差输出的左右顺序，统计排序结果是否改变，降低位置偏差。
- 好、中、差输出和对抗样例使用预先记录的受控错误标签作为参照，例如数字微扰、范围偷换、限制删除和假引用；不把项目作者的单人评分包装成独立人工共识。
- 判别力验证继续保留三档排序准确率和成对排序准确率；删除以人工总分为基准的 Spearman 指标，或将 Spearman 改为自动分数与预设质量等级的等级相关。
- 最终报告如实说明个人项目没有进行多人标注，这是实验边界，不影响完成任务书要求的重复稳定性验证。

### 明确 Hy3 的官方 API 接入名称

- 方案中的“TokenHub API”统一写为“腾讯云大模型服务平台 TokenHub 官方 API”，避免被误解为第三方聚合平台。
- 正式模型参数使用 `hy3`，OpenAI 兼容 Base URL 使用 `https://tokenhub.tencentmaas.com/v1`，实际运行前再通过官方模型列表确认在线状态。
- 不以旧腾讯混元大模型平台作为新项目默认入口。腾讯云官方迁移公告说明旧平台正在迁移至 TokenHub，原平台不再新增模型能力，并计划于 2026-09-30 停止服务。
- 在方案中说明选择 TokenHub 的依据是 Hy3 当前官方可用入口、标准协议兼容、结构化输出能力和迁移方向，而不是因为它比“腾讯云官方 API”更官方。TokenHub 本身就是腾讯云官方 API。

### 确认三阶段版本路线

- MVP 之后只安排两个正式迭代，总计三个版本，避免个人项目因版本过多而失控。
- `V0.1 MVP`：证明技术链路可行。完成单篇 PDF、本科生解读、原子主张、证据绑定、八维文档审计和一次受约束修订。
- `V0.5 协作工作台版`：完成产品体验。提供单一当前文档、点击句子查看证据、句子/段落/章节/全文编辑、与 Hy3 讨论、修改预览、接受/拒绝、增量复核、版本历史和回退。
- `V1.0 完整验证版`：完成可靠性验证和正式交付。运行 45 个好/中/差输出、24 个对抗样例、30 份固定输出各 5 次稳定性实验，并补齐错误归因、成本延迟、README、分析报告和两分钟 demo。
- 三阶段定位统一表述为：`V0.1 证明核心技术，V0.5 完成产品体验，V1.0 用实验数据证明可靠性`。
- 课堂汇报提纲、科普短文、多论文搜索和知识图谱不单独开版本，只能作为核心交付完成后的可选扩展。

### 确认 MinerU 为主 PDF 解析器

- 使用 MinerU `pipeline` 后端作为正式应用和评测的主 PDF 解析器，负责版面、阅读顺序、标题、段落、表格、公式、图片和 OCR 结构化处理。
- 优先消费 MinerU 输出的 Markdown、`content_list_v2.json` 和 `middle.json`，通过独立 `MinerUAdapter` 转换为 PaperLens 自有的 `SourceBlock`，业务模块不得直接依赖 MinerU 原始字段。
- `SourceBlock` 至少保存 `block_id`、`page_index`、`type`、`text`、`bbox`、`reading_order` 和解析器版本，以支持主张证据绑定和页面高亮。
- 前端继续使用 PDF.js 负责 PDF 浏览、翻页、缩放、证据跳转和 bbox 高亮；MinerU 不替代前端阅读器。
- 保留 pdfplumber 作为轻量降级解析器，用于普通文本 PDF、离线单元测试和 MinerU 不可用时的明确降级，不把降级结果伪装成同等解析质量。
- Hy3 仍是项目唯一负责内容生成、原子主张抽取、语义判断、对话修改和修订复核的大模型；MinerU 只属于文档解析基础设施。
- 固定并记录 MinerU 版本、后端和参数。由于不同后端输出存在差异，版本升级必须通过适配器契约测试和解析回归测试。
- README 和必要界面明确标注使用 MinerU，并遵守其当前基于 Apache 2.0、附带额外条件的许可证要求。
- 最终技术表述统一为：`MinerU 负责结构化解析，PDF.js 负责原文展示与证据高亮，Hy3 负责生成、审计和对话式修改，pdfplumber 负责轻量降级`。

### 单一当前文档与对话式编辑工作台

- 产品默认只向用户展示一个持续演进的“当前版本”，不把初稿、审计稿、修订稿和复核稿呈现为四份独立文档。
- 生成、审计、修订和独立复核仍作为内部流程与可展开历史完整保留。
- 用户可以点击句子查看页码、原文证据、支持状态、风险原因和相关原子主张。
- 支持句子、段落、章节和全文四种修改范围，允许用户与 AI 讨论后确认最终内容，交互参考 AI PPT 的单元素与整页修改。
- 局部修改返回结构化补丁，先预览，再由用户接受或拒绝；不得默认重写无关内容。
- 区分“表达修改”和“内容修改”：表达修改锁定事实、数字、限定条件和引用；改变含义的内容修改必须重新检索证据并执行语义审计。
- 局部修改后只复核受影响主张；全文重写后执行完整审计。
- 保存版本历史、修改原因、证据变化和审计结果，并支持回退。

### 新增验收指标

- 句子级修改的无关内容变更率目标不超过 5%。
- 严重非预期事实变更数必须为 0。
- 每次修改必须能说明修改对象、修改原因、事实是否变化、证据是否变化和影响范围。

### 采用核心维度与总分双门槛制

- 最终判定采用“硬失败检查 + 核心维度门槛 + 加权总分门槛”，避免表达或结构高分抵消事实、引用和研究边界方面的严重不足。
- 即使未通过门槛，系统仍计算并展示完整八维分数和加权总分，用于问题诊断；“未达标维度不参与总分计算”的表述不采用，以免删除低分项后反而抬高总分。
- 初始规则为：无硬失败；事实一致性、引用准确性、引用完整性、方法与范围、结论与限制完整性、风险与合规均不低于 3 级；术语准确性、读者适配与结构均不低于 2 级；加权总分不低于 75 分。
- 最终状态分为“合格、待修订、不合格”：全部通过为合格；无硬失败但维度或总分未达标为待修订，可定向修改后重新审计；触发硬失败为不合格，需要重新生成或人工处理。
- `3 级`、`2 级`和 `75 分`均为待校准的初始门槛，不表述为外部统一标准；与分维度区间和权重一起在开发集校准，并在保留集评测前冻结。
- 方案中的正式名称使用“核心维度门槛与总分双门槛制”。

### 同步重构第 12 章预期效果与验收标准

- 将用户价值指标替换为可自动核验的流程指标：5 个预设端到端任务全部通过；点击主张后不超过两次操作可到达页码证据；所有失败路径均有明确状态、错误码或日志。
- 保留关键主张引用准确率、引用完整率、严重错误检出率、已知问题解决率、新增严重错误数、三档判别力、攻击检出率、干净样例误报率、页码映射、结构化输出、成本和失败可诊断性。
- 增加对话式修改指标：句子级修改无关内容变更率不超过 5%，严重非预期事实变更数为 0，每次修改均有对象、原因、事实变化、证据变化和影响范围记录。
- 稳定性验收按 12 份固定输出各 3 次执行：百分制总分平均标准差不超过 5 分，同时报告最大分差和核心维度等级一致率；ICC 只可作为附加描述，不作为硬门槛。
- 判别力实验按 5 篇开发论文各构造好、中、差三档，共 15 份；全排序至少 4/5 正确，成对排序结果报告原始正确对数和比例，不使用过度精确的小样本统计表述。
- 第 12 章增加双门槛验收定义：无硬失败、核心维度达到校准后的下限、所有维度达到最低下限且总分达到校准后的总分线，才标记为“合格”；其余区分“待修订”和“不合格”。
- 所有百分比均明确标记为待实验验证的项目目标或开发集校准结果，不表述为行业统一标准；最终同时报告分子、分母和失败样例。
